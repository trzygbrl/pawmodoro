## 3.1 Interface Type and Rationale

The user interface of an interactive software system establishes the boundary through which human cognitive intent is translated into computational state transitions. In the development of Pawmodoro, the design and implementation of the user interface were dictated by both pedagogical objectives within the computer systems curriculum and strict technical constraints inherent to bare-metal systems programming in 32-bit x86 assembly language under Linux.

### 3.1.1 Identification of Interface Paradigm: Terminal User Interface (TUI)

Pawmodoro implements a **Terminal User Interface (TUI)** operating within standard ANSI/VT100-compliant virtual terminal emulators. Rather than rendering graphical primitives through a windowing compositor or processing stream-oriented command-line invocations, Pawmodoro manages an in-memory two-dimensional grid of text cells (nominally 80 columns by 24 rows). Spatial layout, dynamic visual elements, ASCII character iconography, visual progress bars, and localized color accents are generated by injecting standard ECMA-48 / ANSI escape sequences directly into the standard output stream (`stdout`, file descriptor 1) via direct Linux kernel system calls (`int 0x80`, `SYS_WRITE`).

### 3.1.2 Comparative Rationale: TUI versus CLI and GUI

The selection of a TUI over a pure Command-Line Interface (CLI) or a Graphical User Interface (GUI) was guided by three foundational considerations:

```

+---------------------+-----------------------+-------------------------------+

| / GTK / Qt)         | shared libraries;     | dynamic library dependencies; |
|                     | destroys bare-metal   | obscures processor execution  |
|                     | educational focus.    | and machine registers.        |
```

1. **Comparison with Pure Stream-Based CLI:**  
   Standard command-line utilities (such as `jrnl` or POSIX shell scripts) execute sequentially, emitting output downward into a scrolling buffer and terminating immediately. While appropriate for non-interactive batch pipelines, a pure CLI cannot sustain an interactive, real-time productivity routine. It cannot present a continuous countdown timer, an animated progress indicator, or a persistent habit matrix without continually polluting the terminal scrollback history (Schröder & Cito, 2022). Furthermore, command-line interfaces demand that users recall command flags, file parameters, and invocation syntaxes, increasing cognitive friction. In contrast, a TUI provides a persistent, self-contained dashboard where application state is rendered in place.

2. **Comparison with Graphical User Interfaces (GUI):**  
   Developing a graphical interface under modern Linux distributions requires communicating with the X Window System (X11) via `libX11` / `xcb` or the Wayland display server protocol via `libwayland-client`. These graphics stacks rely on complex asynchronous client-server protocols, dynamic shared object loading (`libc.so`, `libpthread.so`), event dispatch loops, and font-rasterization engines. Introducing graphical subsystems into an assembly project written for an undergraduate Computer Architecture and Organization course obscures the core educational objective: understanding machine-level instructions, processor register allocation, stack frame manipulation, memory addressing modes, and the raw operating system kernel boundary (Gallego-Durán et al., 2021). A GUI framework would reduce assembly code to a mere wrapper around external C runtime libraries.

3. **Alignment with Chapter 2 Foundations:**  
   As established in Chapter 2, Pawmodoro was engineered to demonstrate that a complete, feature-rich productivity environment can be constructed from first principles using pure x86-32 instructions and direct `int 0x80` kernel services. By standardizing on a TUI driven by ANSI escape codes, the entire application maintains a static binary footprint of less than 35 kilobytes, allocates a total memory footprint of under 18 kilobytes in `.bss`, and achieves a 0.0% idle CPU utilization profile without linking against a single external C library or dynamic runtime.

### 3.1.3 Terminal Input Disciplines: Non-Blocking Raw Mode versus Cooked Mode

The human-computer interface of a terminal emulator is governed by the Linux kernel terminal line discipline driver (`termios`). Pawmodoro exploits two distinct operational modes provided by this subsystem:

- **Non-Blocking Raw Mode (`term_raw`):**  
  In default terminal operation, keystrokes are buffered by the kernel line discipline and echoed to the display until the user presses the Enter key (`\n`). In Pawmodoro, interactive navigation across menus and the active execution of the Pomodoro timer require instantaneous keystroke dispatch without requiring line termination or screen corruption.  
  Through the Linux `sys_ioctl` system call (`int 0x80`, `EAX = 54`, `EBX = 0`, `ECX = 0x5402` [`TCSETS`]), the terminal input flags (`c_lflag`) are modified to clear the Canonical Processing (`ICANON`), Echo (`ECHO`), and Signal Interception (`ISIG`) bits:
  $$\text{c\_lflag} \leftarrow \text{c\_lflag} \land \neg(\text{ICANON} \lor \text{ECHO} \lor \text{ISIG})$$
  Simultaneously, the control character parameters are set to `VMIN = 0` and `VTIME = 0`. Under this configuration, the `sys_read` system call queries the keyboard input buffer non-blockingly, returning immediately with available byte sequences or indicating that no key is pending. This enables Pawmodoro's core 10 Hz timing loop in `timer.asm` to maintain an uninterrupted 100-millisecond sleep schedule while concurrently polling for user commands (`P` for Pause, `S` for Skip, `Q` for Stop).

- **Canonical Cooked Mode (`term_cooked`):**  
  While raw mode is ideal for single-stroke command dispatch, text entry (such as typing a new habit description or composing a journal note) requires editing capabilities, including character echo, cursor navigation, and backspace deletion. Pawmodoro temporarily re-engages canonical cooked mode by restoring the original termios structure (`termios_orig`). Under cooked mode, the Linux kernel manages input buffering, multi-byte UTF-8 handling, and line editing internally. Once the user completes the entry with a carriage return, Pawmodoro extracts the NUL-terminated text string, sanitizes the trailing newline, and seamlessly switches back to raw mode.

- **Fault-Tolerant Terminal Restoration:**  
  Because altering terminal line discipline modifies global session parameters, abnormal program termination (such as an unhandled `SIGINT` or `SIGTERM`) risks leaving the user's shell in an unusable, echo-less state. To prevent this, Pawmodoro registers a low-level POSIX signal handler via `sys_sigaction` (`int 0x80`, `EAX = 67`) that intercepts interrupt signals, restores `termios_orig`, switches off the alternate screen buffer (`ESC[?1049l`), restores the cursor (`ESC[?25h`), and terminates gracefully with exit code 130.

### 3.2.3 Screen Dimensions, Frame Design, and Visual Hierarchy

To achieve a professional and distraction-free visual environment, the interface adheres to structured design rules:
1. **Geometric Budgeting:** The interface occupies exactly 56 columns horizontally and 16 to 18 rows vertically, positioned beginning at row 1, column 1. The remaining screen space up to row 24 and column 80 acts as visual margin, preventing border clipping across standard terminal emulators.
2. **Inner Padding and Alignment:** Text labels and status indicators maintain a minimum 2-character interior padding from the outer borders. Dynamic values (such as countdowns, percentages, and tallies) are formatted with fixed-width specifiers (`%02u`) to prevent jittering of adjacent text.
3. **Color-Coded Status Feedback:** ANSI 16-color foreground escape sequences are utilized semantically:
   - **Bold Cyan (`ESC[1;36m`):** Application titles, screen headers, and prominent borders.
   - **Bright Green (`ESC[1;32m`):** Active focus state, completed progress indicators (`#`), and positive status messages.
   - **Bright Yellow (`ESC[1;33m`):** Paused timer state, informational prompts, and demo mode badges.
   - **Bright Blue (`ESC[1;34m`):** Break phase headers and resting cat iconography.
   - **Bright Red (`ESC[1;31m`):** Error alerts, invalid input warnings, and habit deletion prompts.

### 3.3.4 Single-Write Frame Rendering Pipeline

In terminal software development, emitting individual strings or ANSI sequences via separate `sys_write` system calls causes visible screen tearing, flickering, and substantial context-switch overhead across the user-kernel boundary. Pawmodoro eliminates this problem by implementing a buffered frame pipeline centered on `out_buf` (an 8192-byte contiguous memory region in `.bss`) and `out_len` (a 32-bit index).

```
+-----------------------------------------------------------------------------+
|                    BUFFERED FRAME RENDERING PIPELINE                        |
+=============================================================================+
| 1. Frame Preparation:                                                       |
|    - out_len initialized to 0.                                              |
|    - Cursor home sequence (ESC[H) appended.                                 |
+-----------------------------------------------------------------------------+
| 2. In-Memory Frame Construction:                                            |
|    - Outer 56-column ASCII frame boundaries written to out_buf.             |
|    - Text elements, titles, and ASCII cat art positioned via buf_goto.      |
|    - Number formatting (buf_u32, buf_mmss) writes ASCII digits directly.    |
|    - Color attribute escapes injected into buffer stream.                   |
|    - Below-frame region cleared via ESC[J.                                  |
+-----------------------------------------------------------------------------+
| 3. Atomic Kernel Flush (buf_flush):                                         |
|    - Single Linux sys_write(fd=1, buf=out_buf, count=out_len) invocation.   |
|    - Partial write loop and -EINTR signal retry protection.                 |
|    - out_len reset to 0. Zero visual flicker achieved.                      |
+-----------------------------------------------------------------------------+
```

During each render cycle (such as the 10 Hz refresh in `timer.asm`), the entire frame layout—including border coordinates, ASCII art, elapsed time, progress bar brackets, and contextual key hints—is assembled entirely in memory. Only when the frame is fully composed does `buf_flush` issue a single `sys_write` system call. The terminal emulator receives the complete screen update in a single atomic transmission, achieving a completely tear-free presentation.

## 3.4 Data Design

### 3.4.1 Binary Record Layout: `stats.dat` (12 Bytes)

The daily and lifetime Pomodoro statistics are serialized into a fixed-length 12-byte binary file (`stats.dat`). By utilizing binary integer representations rather than parsed ASCII text, serialization and deserialization require zero runtime parsing and are executed via single `sys_read` and `sys_write` system calls.

```
+-----------------------------------------------------------------------------+
|                         STATS.DAT MEMORY LAYOUT                             |
+=============+=============+===============+=================================+
| Byte Offset | Field Name  | Type / Size   | Description                     |
+=============+=============+===============+=================================+
| 0x00 - 0x03 | stats_day   | uint32 (4 B)  | Days elapsed since Unix epoch   |
|             |             |               | (UTC+8 local civil day number)  |
+-------------+-------------+---------------+---------------------------------+
| 0x04 - 0x07 | today_count | uint32 (4 B)  | Completed focus sessions during |
|             |             |               | current calendar day            |
+-------------+-------------+---------------+---------------------------------+
| 0x08 - 0x0B | total_count | uint32 (4 B)  | Cumulative lifetime focus       |
|             |             |               | sessions completed              |
+=============+=============+===============+=================================+
Total Size: 12 Bytes (STATS_RECORD_SIZE)
```

**Day-Rollover Reset Logic:**  
When `stats_load` executes, it compares the stored `stats_day` field against the current local day number returned by `time_today`. If the day numbers match, `today_count` is retained. If the current day is greater than `stats_day`, a midnight rollover has occurred: `stats_day` is updated to today, `today_count` is reset to 0, and `total_count` is preserved intact. If `stats.dat` is missing or corrupted (< 12 bytes), an empty state is established (`today_count = 0`, `total_count = 0`).

### 3.4.2 Binary Record Layout: `habits.dat` (388 Bytes Max)

The habit tracking subsystem maintains an in-memory database of up to 8 habits serialized to `habits.dat`. The file structure consists of a 4-byte header specifying the active habit count ($N \in [0, 8]$) followed by $N$ contiguous 48-byte habit records:

$$\text{File Size} = 4 + (N \times 48) \text{ bytes (Max: 388 bytes)}$$

```
+-----------------------------------------------------------------------------+
|                        HABITS.DAT MEMORY LAYOUT                             |
+=============+=============+===============+=================================+
| Byte Offset | Field Name  | Type / Size   | Description                     |
+=============+=============+===============+=================================+
| 0x00 - 0x03 | habit_count | uint32 (4 B)  | Active habit count (0 to 8)     |
+=============+=============+===============+=================================+
| REPEAT FOR RECORD i = 0 TO (habit_count - 1): Offset = 4 + (i * 48)         |
+-------------+-------------+---------------+---------------------------------+
| +0x00 - 0x1F| name        | char[32] (32B)| NUL-terminated habit name       |
+-------------+-------------+---------------+---------------------------------+
| +0x20 - 0x23| last_day    | uint32 (4 B)  | Day number of most recent check |
+-------------+-------------+---------------+---------------------------------+
| +0x24 - 0x27| streak      | uint32 (4 B)  | Consecutive active days streak  |
+-------------+-------------+---------------+---------------------------------+
| +0x28 - 0x2B| total       | uint32 (4 B)  | Cumulative lifetime check-ins   |
+-------------+-------------+---------------+---------------------------------+
| +0x2C - 0x2F| history     | uint32 (4 B)  | 32-bit completion bitmask       |
|             |             |               | (bit 0 = today, bit k = k days) |
+=============+=============+===============+=================================+
```

**Bitwise Shift Arithmetic for 7-Day Matrix:**  
The `history` field functions as a 32-day sliding bitmask. When a habit check-in is performed, the system calculates the day difference $\Delta = \text{today} - \text{last\_day}$:
- If $\Delta = 0$: The habit was already checked in today; the check-in is rejected to prevent duplicate logging.
- If $\Delta > 0$: The historical bitmask is shifted left by $\Delta$ positions via `SHL EAX, CL`, and bit 0 is set via `OR EAX, 1`:
  $$\text{history} \leftarrow (\text{history} \ll \Delta) \lor 1$$
- Streak calculation: If $\Delta = 1$ (checked in yesterday), the consecutive streak counter is incremented (`streak = streak + 1`). If $\Delta > 1$ (a day was missed), the streak is reset to 1.

### 3.4.3 Append-Only Text Format: `journal.txt`

The journal subsystem records user reflections and post-session focus notes in an append-only, human-readable plain text log (`journal.txt`). Each entry is structured as a single line:

$$\texttt{YYYY-MM-DD HH:MM | } \langle\text{Note Content}\rangle \texttt{\textbackslash n}$$

- **Timestamp Formatting:** Automatically generated from system time adjusted by `TZ_OFFSET` (+28,800 seconds / UTC+8).
- **Text Bounds:** Notes are capped at 72 characters to maintain legibility.
- **Tail-Read Buffer:** Because the file grows monotonically over time, `journal_load_tail` uses `sys_lseek(fd, 0, SEEK_END)` to find the file size. If the file exceeds 4096 bytes, it seeks to $(\text{size} - 4096)$ and reads only the tail, parsing lines backward to display the 10 most recent entries without loading the entire file into memory.

### 3.6.2 Technical Analysis of Extended Instructions (Beyond Chapter 2)

Chapter 2 of the academic proposal established a baseline instruction set consisting primarily of `MOV`, `ADD`, `SUB`, `INC`, `DEC`, `CMP`, `AND`, `OR`, `XOR`, `JMP`, conditional jumps, `CALL`, `RET`, `PUSH`, `POP`, and `INT 0x80` (as illustrated in Chapter 2, Figure 1). During the actual engineering and optimization of the Week 3 prototype, several advanced x86-32 instructions were required to implement time arithmetic, string manipulation, bitmask shifting, and register preservation efficiently.

The technical rationale for incorporating these extended instructions is analyzed below:

1. **`MUL` and `DIV` (Unsigned Multiply and Divide):**  
   - *Where Used:* `time.asm` (civil date conversion, converting epoch seconds to days, hours, and minutes) and `ui.asm` (progress bar fill calculation).  
   - *Technical Necessity:* Chapter 2 did not include hardware multiplication and division. Calculating non-power-of-two arithmetic (such as dividing by 86,400 seconds per day, 3,600 seconds per hour, or multiplying by 30 for bar scaling) using repeated addition or subtraction loops would result in variable-time execution and severe performance degradation. Utilizing `MUL` and `DIV` executes these operations in deterministic hardware clock cycles.
2. **`SHL` and `SHR` (Bitwise Shift Logical Left and Right):**  
   - *Where Used:* `habits.asm` (7-day completion bitmask manipulation and record index scaling).  
   - *Technical Necessity:* In `habits.asm`, tracking daily completion requires shifting a 32-bit history mask by an arbitrary variable number of days $\Delta$ (`SHL EAX, CL`). Implementing variable multi-bit shifts without `SHL` would require software shift loops, whereas `SHL` executes the shift directly using the processor's barrel shifter.
3. **`LEA` (Load Effective Address):**  
   - *Where Used:* `habits.asm` (calculating record base addresses `habits_data + 4 + i * 48`) and `ui.asm`.  
   - *Technical Necessity:* `LEA` performs three-component base-index-displacement address math (`LEA EDI, [EBX + ECX*4 + OFFSET]`) in a single execution cycle without modifying processor status flags (`EFLAGS`), preventing accidental corruption of arithmetic conditions.
4. **`MOVZX` (Move with Zero-Extension):**  
   - *Where Used:* `io.asm`, `term.asm`, `time.asm`.  
   - *Technical Necessity:* Reading single-byte ASCII characters from buffers into 32-bit registers requires zeroing the upper 24 bits. Using `MOVZX EAX, BYTE [ESI]` eliminates the need for separate `XOR EAX, EAX` and `MOV AL, [ESI]` sequences.
5. **`REP MOVSB` and `REP STOSB` (Repeat Move / Store String Byte):**  
   - *Where Used:* `habits.asm` (shifting habit records upon deletion) and `io.asm` (memory zeroing and buffer transfers).  
   - *Technical Necessity:* When a user deletes a habit, all subsequent 48-byte records must be shifted forward in memory. `REP MOVSB` executes block memory transfers at hardware bus speeds utilizing hardware register autoincrement.
6. **`TEST` (Logical Compare / Non-Destructive AND):**  
   - *Where Used:* Across all modules for zero and sign flag verification.  
   - *Technical Necessity:* `TEST EAX, EAX` evaluates whether a system call return value is zero or negative without altering the register content, providing an efficient alternative to `CMP EAX, 0`.
7. **`NEG` (Two's Complement Negation):**  
   - *Where Used:* `time.asm` and `io.asm` for signed arithmetic adjustments.
8. **`CLD` (Clear Direction Flag):**  
   - *Where Used:* Preceding all `REP MOVSB` and `REP STOSB` operations to guarantee forward incrementing memory traversal ($DF = 0$).
9. **`PUSHA` and `POPA` (Push / Pop All General-Purpose Registers):**  
   - *Where Used:* `term.asm` signal handling routines and complex UI subroutines to save and restore `EAX`, `ECX`, `EDX`, `EBX`, `ESP`, `EBP`, `ESI`, and `EDI` atomically.

### 3.7.4 Documented Defects Resolved During Engineering

During prototype development, several critical low-level defects were identified and resolved:
1. **Menu Resize Gate Stall:** When the terminal was resized below 80×24, the application stalled because `read_line` blocked waiting for Enter. *Resolution:* Replaced blocking reads in `main.asm` with non-blocking `key_poll` calls at 100 ms intervals.
2. **Division Overflow in Progress Bar:** Scaling percentages via `DIV` occasionally generated hardware `#DE` (Divide Error) exceptions when `total = 0`. *Resolution:* Added guard check `test ecx, ecx; jz .pb_zero` and cleared `EDX` before all 32-bit divisions.
3. **Cooked Mode Terminal Desynchronization:** Terminating the application via `Ctrl+C` while typing a habit name left the shell terminal in raw mode. *Resolution:* Registered a dedicated `SIGINT` handler restoring `termios_orig` before terminating with exit code 130.

## 3.9 Summary of Chapter 3

Chapter 3 has presented the comprehensive design, requirements, and implementation of the user interface and core subsystems for Pawmodoro. By adopting an ANSI/VT100 Terminal User Interface architecture implemented purely in 32-bit x86 NASM assembly, the project successfully combines an engaging, distraction-free productivity environment with the rigorous pedagogical requirements of low-level systems programming. Through non-blocking raw mode keyboard polling, in-memory single-write frame buffering, robust binary persistence models, and an expanded instruction set incorporating hardware arithmetic, bitmask shifting, and block string transfers, Pawmodoro achieves full functional delivery with zero external runtime dependencies, minimal resource utilization, and robust system stability.
