## 3.1 Interface Type and Rationale

The user interface of an interactive software system establishes the boundary through which human cognitive intent is translated into computational state transitions. In the development of Pawmodoro, the design and implementation of the user interface were dictated by both pedagogical objectives within the computer systems curriculum and strict technical constraints inherent to bare-metal systems programming in 32-bit x86 assembly language under Linux.

### 3.1.1 Identification of Interface Paradigm: Terminal User Interface (TUI)

Pawmodoro implements a **Terminal User Interface (TUI)** operating within standard ANSI/VT100-compliant virtual terminal emulators. Rather than rendering graphical primitives through a windowing compositor or processing stream-oriented command-line invocations, Pawmodoro manages an in-memory two-dimensional grid of text cells (nominally 80 to 100 columns by 24 rows). Spatial layout, dynamic visual elements, ASCII/Unicode character iconography, visual progress bars, and localized 256-color accents are generated by injecting standard ECMA-48 / ANSI escape sequences directly into the standard output stream (`stdout`, file descriptor 1) via direct Linux kernel system calls (`int 0x80`, `SYS_WRITE`).

### 3.1.2 Comparative Rationale: TUI versus CLI and GUI

The selection of a TUI over a pure Command-Line Interface (CLI) or a Graphical User Interface (GUI) was guided by three foundational considerations:

```
|                     | screen persistence.   | countdowns or live cats.      |
+---------------------+-----------------------+-------------------------------+
| GUI (X11 / Wayland  | Requires bloated C    | High overhead; thousands of   |
| / GTK / Qt)         | shared libraries;     | dynamic library dependencies; |
|                     | destroys bare-metal   | obscures processor execution  |
|                     | educational focus.    | and machine registers.        |
+---------------------+-----------------------+-------------------------------+

```

1. **Comparison with Pure Stream-Based CLI:**
   Standard command-line utilities execute sequentially, emitting output downward into a scrolling buffer and terminating immediately. While appropriate for non-interactive batch pipelines, a pure CLI cannot sustain an interactive, real-time productivity routine. It cannot present a continuous countdown timer, an animated progress indicator, or a persistent habit matrix without continually polluting the terminal scrollback history. In contrast, a TUI provides a persistent, self-contained dashboard where application state is rendered in place.

2. **Comparison with Graphical User Interfaces (GUI):**
   Developing a graphical interface under modern Linux distributions requires communicating with the X Window System (X11) via `libX11` / `xcb` or the Wayland display server protocol via `libwayland-client`. These graphics stacks rely on complex asynchronous client-server protocols, dynamic shared object loading (`libc.so`, `libpthread.so`), event dispatch loops, and font-rasterization engines. Introducing graphical subsystems into an assembly project written for an undergraduate Computer Architecture and Organization course obscures the core educational objective: understanding machine-level instructions, processor register allocation, stack frame manipulation, memory addressing modes, and the raw operating system kernel boundary. A GUI framework would reduce assembly code to a mere wrapper around external C runtime libraries.

3. **Alignment with Curriculum Foundations:**
   Pawmodoro was engineered to demonstrate that a complete, feature-rich productivity environment can be constructed from first principles using pure x86-32 instructions and direct `int 0x80` kernel services. By standardizing on a TUI driven by ANSI escape codes, the entire application maintains a static binary footprint of under 35 kilobytes, allocates an in-memory `.bss` budget of 62,392 bytes, and achieves a 0.0% idle CPU utilization profile without linking against a single external C library or dynamic runtime.

### 3.1.3 Terminal Input Disciplines: Non-Blocking Raw Mode versus Cooked Mode

The human-computer interface of a terminal emulator is governed by the Linux kernel terminal line discipline driver (`termios`). Pawmodoro exploits two distinct operational modes provided by this subsystem:

- **Non-Blocking Raw Mode (`term_raw`):**
  In default terminal operation, keystrokes are buffered by the kernel line discipline and echoed to the display until the user presses the Enter key (`\n`). In Pawmodoro, interactive navigation across menus and the active execution of the Pomodoro timer require instantaneous keystroke dispatch without requiring line termination or screen corruption.
  Through the Linux `sys_ioctl` system call (`int 0x80`, `EAX = 54`, `EBX = 0`, `ECX = 0x5402` [`TCSETS`]), the terminal input flags (`c_lflag`) are modified to clear the Canonical Processing (`ICANON`), Echo (`ECHO`), and Signal Interception (`ISIG`) bits:
  $$\text{c\_lflag} \leftarrow \text{c\_lflag} \land \neg(\text{ICANON} \lor \text{ECHO} \lor \text{ISIG})$$
  Simultaneously, the control character parameters are set to `VMIN = 0` and `VTIME = 0`. Under this configuration, the `sys_read` system call queries the keyboard input buffer non-blockingly, returning immediately with available byte sequences or indicating that no key is pending. This enables Pawmodoro's core 10 Hz timing loop in `timer.asm` to maintain an uninterrupted 100-millisecond sleep schedule while concurrently polling for user commands (`P` for Pause, `S` for Skip, `Q` for Stop).

- **Canonical Cooked Mode (`term_cooked`):**
  While raw mode is ideal for single-stroke command dispatch, text entry (such as typing a new habit description or composing a journal note) requires editing capabilities, including character echo, cursor navigation, and backspace deletion. Pawmodoro temporarily re-engages canonical cooked mode by restoring the original termios structure (`termios_orig`). Under cooked mode, the Linux kernel manages input buffering, multi-byte UTF-8 handling, and line editing internally. Once the user completes the entry with a carriage return, Pawmodoro extracts the NUL-terminated text string, sanitizes the trailing newline, and seamlessly switches back to raw mode.

- **Fault-Tolerant Terminal Restoration via `sys_signal` (Syscall 48):**
  Because altering terminal line discipline modifies global session parameters, abnormal program termination (such as an unhandled `SIGINT`, `SIGTERM`, or `SIGHUP`) risks leaving the user's shell in an unusable, echo-less state. To prevent this, Pawmodoro registers a low-level POSIX signal handler using the Linux `sys_signal` system call (`int 0x80`, `EAX = 48`, `EBX = signum`, `ECX = handler_addr`). Pawmodoro deliberately utilizes `sys_signal` rather than `sys_sigaction` (syscall 67) to avoid allocating multi-dword `sigaction` structures in memory, saving binary space while providing direct kernel interrupt vectoring for `SIGHUP`, `SIGINT`, and `SIGTERM` in `term.asm`, as well as `SIGPIPE` and `SIGCHLD` in `sfx.asm`. When an exit signal is received, the handler immediately restores `termios_orig`, deactivates the alternate screen buffer (`ESC[?1049l`), restores cursor visibility (`ESC[?25h`), and terminates gracefully with exit code 130.

### 3.2.3 Screen Dimensions, Frame Design, and Visual Hierarchy

To achieve a professional, distraction-free visual environment, the interface adheres to structured design rules:
1. **Dynamic Geometric Budgeting:** The interface occupies between 78 and 100 columns horizontally and 22 to 24 rows vertically. The dynamic width calculation ensures balanced margins across widescreen terminal windows while maintaining compatibility with 80×24 standards.
2. **Inner Padding and Alignment:** Text labels and status indicators maintain a minimum 2-character interior padding from outer borders. Dynamic values (countdowns, percentages, streaks) are formatted with fixed-width specifiers (`%02u`) to prevent jittering of adjacent text.
3. **256-Color Semantic Hierarchy:** Palettes map to 12 abstract color slots:
   - **Slot 0 (Background):** Base terminal canvas color.
   - **Slot 1 (Border):** Outer box-drawing frame and dividers.
   - **Slot 2 (Normal Text):** Body labels, menu options, table rows.
   - **Slot 3 (Dim Text):** Tips, secondary headers, inactive status.
   - **Slot 4 (Accent Primary):** Screen titles, focused highlights.
   - **Slot 5 (Accent Secondary):** Cat art features, sub-headings.
   - **Slot 6 (Success / Focus):** Active countdown, completed habits, focus progress.
   - **Slot 7 (Warning / Pause):** Paused state indicator, demo mode badge.
   - **Slot 8 (Break / Rest):** Short/long break phase headers, resting cat art.
   - **Slot 9 (Error):** Alert prompts, habit deletion warnings.
   - **Slot 10 (Highlight):** Selected menu item or active journal entry.
   - **Slot 11 (Extra):** Auxiliary badge highlights.

### 3.3.4 Single-Write Frame Rendering Pipeline

In terminal software development, emitting individual strings or ANSI sequences via separate `sys_write` system calls causes visible screen tearing, flickering, and substantial context-switch overhead across the user-kernel boundary. Pawmodoro eliminates this problem by implementing a buffered frame pipeline centered on `out_buf` (an 8,192-byte contiguous memory region in `.bss`) and `out_len` (a 32-bit index).

```
+-----------------------------------------------------------------------------+
|                    BUFFERED FRAME RENDERING PIPELINE                        |
+=============================================================================+
| 1. Frame Preparation:                                                       |
|    - out_len initialized to 0.                                              |
|    - Cursor home sequence (ESC[H) appended.                                 |
+-----------------------------------------------------------------------------+
| 2. In-Memory Frame Construction:                                            |
|    - Adaptive outer frame boundaries written to out_buf.                    |
|    - Text elements, titles, and ASCII cat art positioned via buf_goto.      |
|    - Number formatting (buf_u32, buf_mmss) writes ASCII digits directly.    |
|    - 256-color escape sequences injected via theme_color.                   |
|    - Below-frame region cleared via ESC[J.                                  |
+-----------------------------------------------------------------------------+
| 3. Atomic Kernel Flush (buf_flush):                                         |
|    - Single Linux sys_write(fd=1, buf=out_buf, count=out_len) invocation.   |
|    - Partial write loop and -EINTR signal retry protection.                 |
|    - out_len reset to 0. Zero visual flicker achieved.                      |
+-----------------------------------------------------------------------------+
```

During each render cycle (such as the 10 Hz refresh in `timer.asm`), the entire frame layout—including border coordinates, ASCII art, elapsed time, progress bar brackets, and contextual key hints—is assembled entirely in memory. Only when the frame is fully composed does `buf_flush` issue a single `sys_write` system call. The terminal emulator receives the complete screen update in a single atomic transmission, achieving a completely tear-free presentation.

## 3.4 Data Design

### 3.4.1 Binary Record Layout: `stats.dat` (12 Bytes)

The daily and lifetime Pomodoro statistics are serialized into a fixed-length 12-byte binary file (`stats.dat`). By utilizing binary integer representations rather than parsed ASCII text, serialization and deserialization require zero runtime parsing and are executed via single `sys_read` and `sys_write` system calls.

```
+-----------------------------------------------------------------------------+
|                         STATS.DAT MEMORY LAYOUT                             |
+=============+=============+===============+=================================+
| Byte Offset | Field Name  | Type / Size   | Description                     |
+=============+=============+===============+=================================+
| 0x00 - 0x03 | stats_day   | uint32 (4 B)  | Days elapsed since Unix epoch   |
|             |             |               | (UTC+8 local civil day number)  |
+-------------+-------------+---------------+---------------------------------+
| 0x04 - 0x07 | today_count | uint32 (4 B)  | Completed focus sessions during |
|             |             |               | current calendar day            |
+-------------+-------------+---------------+---------------------------------+
| 0x08 - 0x0B | total_count | uint32 (4 B)  | Cumulative lifetime focus       |
|             |             |               | sessions completed              |
+=============+=============+===============+=================================+
Total Size: 12 Bytes (STATS_RECORD_SIZE)
```

**Day-Rollover Reset Logic:**
When `stats_load` executes, it compares the stored `stats_day` field against the current local day number returned by `time_today`. If the day numbers match, `today_count` is retained. If the current day is greater than `stats_day`, a midnight rollover has occurred: `stats_day` is updated to today, `today_count` is reset to 0, and `total_count` is preserved intact. If `stats.dat` is missing or corrupted (< 12 bytes), an empty state is established (`today_count = 0`, `total_count = 0`).

### 3.4.2 Binary Record Layout: `habits.dat` (388 Bytes Max)

The habit tracking subsystem maintains an in-memory database of up to 8 habits serialized to `habits.dat`. The file structure consists of a 4-byte header specifying the active habit count ($N \in [0, 8]$) followed by $N$ contiguous 48-byte habit records:

$$\text{File Size} = 4 + (N \times 48) \text{ bytes (Max: 388 bytes)}$$

```
+-----------------------------------------------------------------------------+
|                        HABITS.DAT MEMORY LAYOUT                             |
+=============+=============+===============+=================================+
| Byte Offset | Field Name  | Type / Size   | Description                     |
+=============+=============+===============+=================================+
| 0x00 - 0x03 | habit_count | uint32 (4 B)  | Active habit count (0 to 8)     |
+=============+=============+===============+=================================+
| REPEAT FOR RECORD i = 0 TO (habit_count - 1): Offset = 4 + (i * 48)         |
+-------------+-------------+---------------+---------------------------------+
| +0x00 - 0x1F| name        | char[32] (32B)| NUL-terminated habit name       |
+-------------+-------------+---------------+---------------------------------+
| +0x20 - 0x23| last_day    | uint32 (4 B)  | Day number of most recent check |
+-------------+-------------+---------------+---------------------------------+
| +0x24 - 0x27| streak      | uint32 (4 B)  | Consecutive active days streak  |
+-------------+-------------+---------------+---------------------------------+
| +0x28 - 0x2B| total       | uint32 (4 B)  | Cumulative lifetime check-ins   |
+-------------+-------------+---------------+---------------------------------+
| +0x2C - 0x2F| history     | uint32 (4 B)  | 32-bit completion bitmask       |
|             |             |               | (bit 0 = today, bit k = k days) |
+=============+=============+===============+=================================+
```

**Bitwise Shift Arithmetic for 7-Day Matrix:**
The `history` field functions as a 32-day sliding bitmask. When a habit check-in is performed, the system calculates the day difference $\Delta = \text{today} - \text{last\_day}$:
- If $\Delta = 0$: The habit was already checked in today; the check-in is rejected to prevent duplicate logging.
- If $\Delta > 0$: The historical bitmask is shifted left by $\Delta$ positions via `SHL EAX, CL`, and bit 0 is set via `OR EAX, 1`:
  $$\text{history} \leftarrow (\text{history} \ll \Delta) \lor 1$$
- Streak calculation: If $\Delta = 1$ (checked in yesterday), the consecutive streak counter is incremented (`streak = streak + 1`). If $\Delta > 1$ (a day was missed), the streak is reset to 1.

### 3.4.3 Append-Only Text Format: `journal.txt`

The journal subsystem records user reflections and post-session focus notes in an append-only, human-readable plain text log (`journal.txt`). Each entry is structured as a single line:

$$\texttt{YYYY-MM-DD HH:MM | } \langle\text{Note Content}\rangle \texttt{\textbackslash n}$$

- **Timestamp Formatting:** Automatically generated from system time adjusted by `TZ_OFFSET` (+28,800 seconds / UTC+8).
- **Text Bounds:** Notes are accepted up to 200 characters (`JOURNAL_ENTRY_MAX = 200`), accommodating detailed multi-sentence reflections. In the list view, entries exceeding visible row width are truncated with an ellipsis or wrapped with a 4-space continuation indent. Pressing `Enter` opens the Full Entry View modal, where notes are word-wrapped cleanly across up to 10 lines.
- **Tail-Read Buffer:** Because the file grows monotonically over time, `journal_load_tail` uses `sys_lseek(fd, 0, SEEK_END)` to find the file size. If the file exceeds 16,384 bytes, it seeks to $(\text{size} - 16384)$ and reads only the tail, parsing lines backward to display recent entries without loading the entire file into memory.

## 3.6 Architecture and Implementation of Version 2.0 Features

This section documents the technical architecture, algorithms, and assembly implementations of the major Version 2.0 feature additions: adaptive terminal layouts, 256-color theme engine, event-driven animation, integer sound synthesis with external audio streaming, atomic journal deletion, and layered terminal notifications.

### 3.6.1 Adaptive Layout Engine (`ui.asm`)

Version 1 enforced a rigid, fixed 56-column frame. Version 2 introduces an adaptive layout engine that queries terminal geometry dynamically via `sys_ioctl(TIOCGWINSZ)` and sizes the application interface to fit modern terminal windows:
- **Geometry Bounds:** Requires a minimum geometry of 80 columns by 24 rows (`TERM_MIN_COLS = 80`, `TERM_MIN_ROWS = 24`). If the window falls below either threshold, the synchronous safeguard gate `ui_size_gate` halts normal rendering and displays an informative resize prompt.
- **Adaptive Frame Width:** On terminals wider than 80 columns, the layout dynamically widens up to 100 columns (`UI_FRAME_MAX_WIDTH = 100`). The frame width `ui_w` is computed as:
  $$\text{ui\_w} = \min(\text{term\_cols} - 2, 100)$$
- **Horizontal Centering:** The frame is centered within the terminal by computing a horizontal margin offset `ui_col0 = (\text{term\_cols} - \text{ui\_w}) / 2`. All cursor positioning calls throughout the rendering pipeline add `ui_col0` to local column coordinates.

```nasm
; src/ui.asm lines 526-533: Adaptive frame width calculation
    ; ui_w = min(term_cols - 2, 100)
    sub eax, UI_FRAME_MARGIN_COLS ; term_cols - 2
    cmp eax, UI_FRAME_MAX_WIDTH  ; 100
    jbe .w_ok
    mov eax, UI_FRAME_MAX_WIDTH
.w_ok:
    mov [ui_w], eax
```
*Technical Context:* This concise logic inspects the terminal column count in `EAX`, subtracts the outer margin columns, clamps the maximum width to 100 via an unsigned compare (`CMP/JBE`), and stores the calculated width in `ui_w`.

### 3.6.2 Color Palette and Theme System (`theme.asm`)

Pawmodoro implements an abstract 12-slot color palette model supporting eight distinct themes: Default Amber, Catppuccin Mocha, Nord, Tokyo Night, Solarized Dark, Gruvbox, Cyberpunk, and Custom Palette.
- **Slot Abstraction:** Visual components request colors semantically (e.g., `SLOT_BORDER`, `SLOT_ACCENT_PRIMARY`, `SLOT_SUCCESS`) rather than hardcoding ANSI escape codes.
- **Color Sequence Injection:** The procedure `theme_color` takes a slot index in `AL`, bounds-checks the index against `NUM_SLOTS = 12`, retrieves the 256-color index byte from `active_palette`, and formats the extended ANSI sequence `ESC[38;5;<index>m` directly into `out_buf`.
- **Custom Palette Editing:** Selecting Theme 7 activates the in-memory custom palette, which allows users to interactively modify individual ANSI color values (0–255) across all 12 slots and preview results in real time.

```nasm
; src/theme.asm lines 37-50: 12-slot color lookup and ANSI escape formatting
    ; Look up 256-color byte (0..255) from active_palette
    movzx ebx, al
    movzx eax, byte [active_palette + ebx]

    ; 1. Emit foreground sequence prefix: ESC[38;5;
    mov esi, ansi_fg_256_prefix
    call buf_str

    ; 2. Emit unsigned decimal color index (0..255)
    call buf_u32

    ; 3. Emit closing letter 'm'
    mov al, CHAR_LOWER_M
    call buf_char
```
*Technical Context:* The routine uses `MOVZX` to zero-extend the slot index, retrieves the active color index from `active_palette`, and injects the standardized ECMA-48 extended color escape sequence into the output buffer.

### 3.6.3 Lightweight Animation Engine (`anim.asm`)

The animation engine introduces multi-frame ASCII cat animations (blinking eyes, flicking tail, breathing motion, and purring) during active and resting timer phases:
- **Tick Cadence & Throttling:** Driven by the existing 100 ms `timer.asm` loop (10 Hz). To prevent excessive terminal I/O and conserve host battery life, `anim_render` enforces a maximum write ceiling of 5 frames per second (at least 200 ms between frame updates via `ANIM_THROTTLE_TICKS = 2`).
- **Dirty-Cell Region Gating:** The engine tracks visual state changes using bitwise dirty flags (`anim_dirty_flags`). If no visual elements have transitioned, frame flushes are bypassed entirely.
- **Reduce Motion:** When the user enables Reduce Motion in Settings (`setting_anim = 0`), all animation state accumulation and idle frame emissions are suppressed, resulting in strictly zero idle `sys_write` calls and 0.0% CPU overhead.

```nasm
; src/anim.asm lines 943-955: Multi-gate animation render throttle
    ; Gate 2: Terminal minimum size gate
    call term_size_ok
    test eax, eax
    jz .render_done

    ; Gate 3: Dirty flags check
    mov eax, [anim_dirty_flags]
    test eax, eax
    jz .render_done

    ; Gate 4: Write throttle ceiling (at least 2 ticks = 200ms elapsed)
    cmp dword [anim_throttle_count], ANIM_THROTTLE_TICKS
    jb .render_done
```
*Technical Context:* Before emitting an animated update, the engine verifies that the terminal geometry is valid, checks whether visual cells are marked dirty, and confirms that the 200 ms throttle window has elapsed.

### 3.6.4 Sound Synthesis and Playback Architecture (`sfx.asm`)

Pawmodoro synthesizes retro audio feedback directly in software without relying on external `.wav` files, audio libraries, or floating-point instructions:
- **Pure Integer Waveform Synthesis:** Implements square-wave, triangle-wave, and pseudo-random noise algorithms using 32-bit integer arithmetic. Samples are synthesized at 44.1 kHz, 16-bit signed mono into an internal 32,768-byte buffer (`sfx_buf`).
- **External Player Invocation:** Because 32-bit Linux assembly applications cannot directly talk to PulseAudio or PipeWire daemon sockets without complex library bindings, Pawmodoro utilizes an external playback streaming architecture. It creates an IPC pipe via `sys_pipe`, forks a child process via `sys_fork`, redirects the pipe to `stdin` using `sys_dup2`, and executes `paplay` or `aplay` via `sys_execve`.
- **Fault-Tolerant Degradation:** If neither external player is available on the system, the child process exits cleanly with status 127. The parent process handles `SIGPIPE` and `SIGCHLD` safely with zero zombie processes, and gracefully falls back to emitting the ASCII terminal bell (`\a`).

```nasm
; src/sfx.asm lines 247-258: Square wave integer audio synthesis and centering
    ; Phase accumulator MSB (bit 31): 0 = high (+A), 1 = low (-A)
    test ebp, 0x80000000
    jnz .square_low
    mov eax, ebx                ; +A(t)
    jmp .apply_center

.square_low:
    mov eax, ebx
    neg eax                     ; -A(t)

.apply_center:
    ; Add unsigned 8-bit PCM center (128)
    add eax, PCM_CENTER
```
*Technical Context:* Demonstrating integer waveform generation, the code tests the phase accumulator's sign bit to produce alternating high and low amplitude phases, using `NEG` to invert amplitude before adding the PCM midpoint offset.

### 3.6.5 Atomic Journal Deletion via Staging and Rename (`file.asm`)

The journal subsystem supports in-place deletion of individual entries without risking data corruption in the event of an unexpected power failure or crash:
- **Staging Rewrite Pipeline (`file_delete_range`):** When an entry is selected for deletion, the application calculates the entry's byte range `[start_off, end_off]`. It opens `journal.txt` for reading and creates a staging file `journal.tmp` using flags `O_WRONLY | O_CREAT | O_TRUNC` (`0644`).
- **Chunked Transfer:** The engine copies surviving bytes preceding `start_off` in 2,048-byte chunks (`del_copy_buf`), skips the deleted range, and copies all remaining bytes following `end_off`.
- **Atomic POSIX Replacement:** Once all surviving bytes are written, both descriptors are closed, and `sys_rename` (syscall 38) replaces `journal.txt` with `journal.tmp` atomically. If any error occurs during staging, `journal.tmp` is unlinked and `journal.txt` remains completely intact.

```nasm
; src/file.asm lines 357-369: Descriptor closure and atomic sys_rename replacement
    ; 10. Close both file descriptors unconditionally
    mov ebx, [ebp - 20]         ; fd_out
    syscall SYS_CLOSE, ebx
    mov ebx, [ebp - 16]         ; fd_in
    syscall SYS_CLOSE, ebx

    ; 11. Atomic rename: rename(path_journal_tmp, orig_path)
    mov ebx, path_journal_tmp   ; oldpath
    mov ecx, [ebp - 24]         ; newpath
    syscall SYS_RENAME, ebx, ecx
    test eax, eax
    jnz .del_rename_failed
```
*Technical Context:* Both file descriptors are closed to flush operating system file caches before `sys_rename` is dispatched, ensuring POSIX file system atomicity during entry removal.

### 3.6.6 Layered Terminal Notifications

Pawmodoro implements five configurable notification layers to alert users when a focus session or break finishes:
1. **Audible / Visual Bell (`\a`):** Standard ASCII bell character (byte `0x07`).
2. **Terminal Screen Flash:** Temporarily asserts reverse video mode (`ESC[?5h`), pauses briefly, and clears it (`ESC[?5l`), providing silent visual alerting.
3. **Dynamic Window Title:** Emits `ESC]0;Pawmodoro - Focus Complete!\a` (OSC 0) to update the terminal emulator title bar.
4. **Taskbar Progress State:** On compatible terminals (such as Windows Terminal), emits OSC 9;4 sequences (`ESC]9;4;1;100\a`) to update taskbar progress bars.
5. **Desktop Notifications:** Emits standard OSC 777 / OSC 9 escape sequences to trigger native host operating system desktop toast notifications where supported.

### 3.7.2 Technical Analysis of Executable Instructions and Audit Findings

An exhaustive automated audit of all executable instructions across `src/` yielded the following technical findings:

1. **`PUSHA` and `POPA` Instructions:**
   - *Audit Finding:* **Zero executable occurrences.** Neither `PUSHA` nor `POPA` appears as an executable instruction in any source module.
   - *Architectural Rationale:* As documented in `src/macros.inc:41`, `POPA` unconditionally overwrites `EAX`, preventing subroutines and system call wrappers from returning status codes or values in `EAX`. Pawmodoro explicitly defines `save_regs` and `restore_regs` macros that preserve only `EBX`, `ECX`, `EDX`, `ESI`, and `EDI` via discrete `PUSH`/`POP` instructions, keeping `EAX` available for return data.
2. **`LOOP` Instruction:**
   - *Audit Finding:* **Zero executable occurrences.** The `LOOP` mnemonic appears only in comments and label names (such as `.flush_write_loop`).
   - *Architectural Rationale:* The legacy x86 `LOOP` instruction is microcode-heavy and relatively slow on modern x86 microarchitectures compared to `DEC ECX; JNZ ...`. All iteration loops in Pawmodoro are implemented using standard conditional branches.
3. **`NEG` Instruction:**
   - *Audit Finding:* **Exactly one verified executable occurrence.** Located at `src/sfx.asm:254` within the integer audio synthesizer.
   - *Architectural Rationale:* Used to invert audio sample amplitudes during square and triangle waveform generation (`neg eax ; -A(t)`). It is not used in `time.asm` or `io.asm`, which perform all calendar and coordinate arithmetic using unsigned integer math.
4. **`MUL` and `DIV` Instructions:**
   - *Where Used:* `time.asm` (epoch civil date conversion), `ui.asm` (progress bar scaling), and `sfx.asm` (frequency phase accumulator math).
   - *Architectural Role:* Enables deterministic hardware-accelerated clock cycle execution for non-power-of-two arithmetic without requiring floating-point coprocessors.
5. **`SHL` and `SHR` Instructions:**
   - *Where Used:* `habits.asm` (7-day completion bitmask sliding) and `sfx.asm` (PCM volume scaling).
   - *Architectural Role:* Executes variable multi-bit shifts in a single clock cycle using the processor's barrel shifter.
6. **`REP MOVSB` and `REP STOSB` Instructions:**
   - *Where Used:* `habits.asm` (record shifting upon row deletion), `file.asm` (buffer staging), and `io.asm` (buffer clearing).
   - *Architectural Role:* Maximizes memory transfer throughput at hardware bus speeds utilizing register auto-incrementing. Preceded by `CLD` to enforce forward memory traversal ($DF = 0$).

## 3.10 Summary of Chapter 3

Chapter 3 has presented the comprehensive design, requirements, and implementation of the user interface and core subsystems for Pawmodoro. By adopting an ANSI/VT100 Terminal User Interface architecture implemented purely in 32-bit x86 NASM assembly, the project successfully combines an engaging, distraction-free productivity environment with the rigorous pedagogical requirements of low-level systems programming. Through non-blocking raw mode keyboard polling, in-memory single-write frame buffering, adaptive terminal layout scaling, integer waveform sound synthesis, robust binary persistence models, and an expanded instruction set incorporating hardware arithmetic, bitmask shifting, and block string transfers, Pawmodoro achieves full functional delivery with zero external runtime dependencies, minimal resource utilization, and robust system stability.
