## Part 1 — Read first: what is possible, and the decisions I made

**1. How a terminal can look like that image.** Plain text characters cannot draw round, soft cats. The trick that makes a terminal look like a GUI is **half-block pixel art**: the character `▀` (upper half block) has a foreground color for its top half and a background color for its bottom half, so **one terminal cell = two vertically stacked pixels** (and terminal cells are about twice as tall as wide, so those pixels come out roughly square). With 256-color escapes, a 16×12-cell sprite is a 16×24-pixel colored picture. That is how the cats, tomato, icons, and big digits are drawn. It is still assembly: the sprites are data tables and a small rendering loop (`MOVZX`, shifts, table lookups, `rep`-style loops).

**2. Honest limits.** Resolution is low (the whole screen is only ~120×48 "pixels" at a 120×24 window), so tiny details (single whiskers, glow, soft gradients) are approximated with 256-color ramps and shade glyphs `░▒▓`. Expect "clearly the same design and mascot style", not a pixel-perfect copy. The title bar with the minimize/maximize/close buttons in your image is **your terminal window's own title bar**; the app can only set its text (`PAWMODORO ✦`, already supported by the title layer).

**3. "Very accurate" art needs a source of truth.** An AI cannot reliably invent good pixel art from a description. Decision: **sprites are authored from your reference images.** Put the full mockup in `docs/reference/` and crop each element (logo cat, tomato mascot, habits cat head, sleeping cat, each icon) into `docs/reference/sprites/*.png`. A **dev-only converter** (`tools/png2sprite.py`, needs Python + Pillow; it is a build helper, **not** part of the app) downsizes a crop to a given cell size, snaps to your theme's art slots, and writes assembly data. The running app stays 100% assembly. If you prefer no Python at all, G3 can instead use hand-typed pixel grids (more work, less accurate). **Default: converter allowed.**

**4. Colors stay customizable.** Sprites do not store colors. They store **palette numbers that map to theme color slots** (fur, fur shade, ear/blush, outline, eye, nose, tomato, leaf…), so changing the theme or editing a slot in Settings recolors the art. A **Cat coat** setting (orange tabby, gray, black, white, cream, tuxedo) recolors only the fur. **Default: 256-color only** (a true-color mode is a stretch goal).

**5. The app paints its own background.** Your image has a dark surface. The app fills the screen with a background slot color once per full redraw (`ESC[48;5;Nm` + `ESC[2J`; most terminals fill with the current background). Panels and cards use their own surface slots. The terminal returns to normal on exit (already handled by `term_restore`).

**6. Layout tiers, because 80×24 cannot hold the mockup.** The mockup is about 120 columns wide. **Default tiers:** *Compact* (80–99 cols or < 30 rows: 1-row sidebar buttons, 2×2 cards, small sprites), *Standard* (≥ 100×30) and *Grand* (≥ 120×36: the image layout with 3-row bordered buttons, big mascot, vines). Minimum stays 80×24. The frame width cap rises from 100 to 120 (amends PRD v2 §2).

**7. Mouse (the biggest "this is not a terminal" feeling).** Decision: **click support via xterm SGR mouse reporting** (works in Windows Terminal, GNOME Terminal, tmux). Click a sidebar button, a toggle switch, a habit row, a journal entry. Keyboard keeps working everywhere, and a Settings toggle turns the mouse off. Hover effects are a stretch goal (they flood the input with events).

**8. Pixel art replaces emoji.** Emoji are double-width and break alignment (PRD v2 §3). Tomato, paw, gear, exit door, checklist, book, stars and vines are all small sprites instead. New approved glyphs: `▀ ▄ █ ▌ ▐ ░ ▒ ▓ ✓`. Every sprite needs an ASCII-mode text-art variant (no byte ≥ 0x80).

**9. Memory budget (important).** A half-block cell with both colors costs ~25 bytes (`ESC[38;5;Nm ESC[48;5;Nm ▀`). The current `out_buf` is **8,192 B**; one big mascot would overflow it and the overflow is silently dropped (corrupted frame). Decision: **`out_buf` grows to 16,384 B** (+8,192 → `.bss` ≈ 70.6 KB of the 80 KiB cap) and sprite drawing skips escape codes when the color did not change. Sprite data lives in `.data` as run-length-encoded bytes (cap ~24 KB so the ELF stays under the ~64 KB goal).

**10. Heads-up: things I found in the repo that this roadmap also fixes (G14/G15).**
- `ui_frame_hline` chooses top/middle/bottom borders from **hard-coded row numbers and `[state]`** (rows 10, 16, 17, 22, 23). That cannot support a free layout; G6 replaces it with explicit rectangle-based drawing.
- Smoke scenarios **27, 29, 30, 31** write `settings.dat` with magic `PAWM` and a wrong length; the loader requires `PAWS`, version 1 and exactly 24 bytes, so these tests probably run with **default** settings and pass without testing what they claim. Scenarios 21 and 29 also `rm` the strace log while strace still writes it, so "0 idle writes" is read from a file that no longer exists. Scenario 19/27 use `grep -P "[\x80-\xFF]"`, which in a UTF-8 locale does not match what you want. Please do not trust those five checks until G14 rewrites them.
- Docs drift: the README `settings.dat` layout, the Chapter 3 draft (big 5-line digits, a "Bell" setting, `C`/`R` keys in Settings, Catppuccin/Nord themes, 44.1 kHz audio) do not match the code (11,025 Hz 8-bit; themes Strawberry Milk…High Contrast; no big digits yet). G15 corrects them.

**11. Decisions I need from you (my default in bold).**
(a) Converter script allowed? **Yes.** (b) Mouse? **Yes, click only.** (c) Quick Journal card content (the mockup's card only shows decorative labels): **last 3 journal entries**, with the *Quick Journal* button opening the new-entry prompt directly. (d) Light themes (light terminal backgrounds)? **No, dark surfaces only for v3.** (e) Default theme: **Strawberry Milk becomes the dark-surface pink look from your image.**

## Tips for getting the best-looking result

- **Use a good terminal font** with block-element support (Cascadia Mono/Code in Windows Terminal, JetBrains Mono, Fira Code). Set the cell height so rows look about twice as tall as columns; pixel art assumes that.
- **Test in the Grand size** (120×36) for screenshots, but always re-check 80×24: that is what a grader's default window might be.
- **Review art early.** After G4 and G5 look at every sprite in the viewer before building screens on top. Re-cropping a sprite is cheap now and expensive after G7.
- **One task per session, commit after each.** G4 and G5 are the longest; if an agent session runs out of room, split by sprite group and run the same paragraph twice with a shorter sprite list.
